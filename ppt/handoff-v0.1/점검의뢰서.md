# 점검의뢰서 — PPT 프레임워크 v0.1

## 대상과 목적
이 패키지는 한국 보험사 내부 보고용 PPT 프레임워크의 첫 성문화본이다.
이 프레임워크는 지금까지 특정 대화의 맥락 안에서 만들어졌고, 이번 점검의 목적은 **맥락 없이 문서만으로 자립하는지**를 검증하는 것이다. 점검자는 원 대화를 볼 수 없으며, 그것이 이 점검의 가치다.

## 점검 범위의 경계 (중요)
- 판단할 것: 규칙의 **일관성·완결성·실행가능성**
- 판단하지 말 것: 규칙의 **적합성** — "이 규칙이 이 조직·이 보고 문화에 맞는가"는 조직 맥락이 문서 밖에 있으므로 점검 불가. 적합성 판단을 시도하지 말고, 적합성 검증에 필요한데 문서에 없는 정보가 있으면 "누락 정보"로만 보고할 것
- 점검자와 원 작성자는 같은 모델 계열이다. 이 점검은 제3자 검증이 아니라 **컨텍스트 교차 검증**임을 전제로 수행할 것

## 점검 항목 (5)

### 1. 모순 검사
룰북 전체에서 조항 간 충돌을 찾는다.
- 필수 확인: L5(잉크 최소화) × 챕터 2(밀도 요구)의 화해 조항이 문서에 명시돼 있고, 그 조항만으로 실제 판단이 가능한가. 화해 조항이 커버하지 못하는 충돌 사례를 최소 2개 구성해볼 것
- 챕터 1 문장부호 규정과 챕터 2 주석 레이어·차트 규정 간 충돌 여부
- CLAUDE.md 요약과 룰북 본문의 불일치

### 2. 과적합 검사
챕터 2(시각)는 벤치마크 1개에서 추출됐다.
- 조항별로 [일반 원칙으로 승격 가능 / 벤치마크 표본 확대 필요 / 해당 벤치마크 특수성]을 분류하고 사유를 붙일 것
- 표본 확대가 필요한 조항에 대해, 어떤 종류의 덱 몇 건을 더 보면 판정 가능한지 제안

### 3. 자립 드라이런 (가장 중요)
문서만 읽고, 아래 가상 안건으로 파이프라인 1~4단계를 실제로 수행하라.
- 가상 안건: "건강증진형 정기보험 파일럿 컨셉을 부서장에게 보고해 방향 동의를 얻는 덱" (오디언스 프라이어는 스스로 그럴듯하게 가정하되 가정임을 명시)
- 산출: 정의서 답안, 체인(4~6줄), 구멍 검사 결과, 장 1개의 폼 스터디 선택과 사유
- **수행 중 문서가 답을 주지 못해 막힌 지점, 해석이 두 갈래로 갈린 지점을 전부 기록하라.** 이 기록이 드라이런의 핵심 산출물이다. 산출물의 품질 자체는 부차적이다

### 4. 코드 리뷰
- code/form-study.jsx: JSON 스키마 견고성, 에러 경로, 프롬프트가 룰북 §8과 일치하는지, storage 사용의 결함
- code/build_v5r.js: 룰북 챕터 1·2 규정의 준수 여부를 코드 레벨에서 확인 (이 파일은 규정의 참조 구현체다). 규정과 코드가 어긋나는 지점을 목록화
- samples/의 pptx는 build_v5r.js의 산출물이다. 필요 시 텍스트를 추출해 대조하라

### 5. 사양 타당성
spec/덱보드_v0.1_사양.md를 검토하고 문서 말미의 "점검 요청 사항" 4개에 답하라.

## 산출물 형식
저장소 루트에 `점검결과.md` 생성. 구성:
1. 요약 (5줄 이내)
2. 항목 1~5 결과
3. **우선순위 픽스 목록** — [치명/중요/권장] 태그, 각 항목에 구체 수정안 1개 이상
4. 룰북 v0.2에 추가돼야 할 신규 조항 제안 (있다면)

## 시작 방법
이 문서를 읽었다면: rulebook/룰북_v0.1.md → CLAUDE.md → spec → code 순으로 읽고 점검을 시작하라.
